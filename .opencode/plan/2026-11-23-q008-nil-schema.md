# qi-json — report a nil nested `Schema` in `Object` instead of panicking

**Date**: 2026-11-23
**Related**: `docs/panics-issues.md` (Issue 3), `docs/tasks.md` (Q008),
`internal/codec/field.go`, `internal/codec/sentinel_test.go`.

This file is a design record. Task state lives in `docs/tasks.md`.

---

## 1. Why (the defect)

`Object` binds a nested struct field to another `*Schema[S]`, but it stored the
pointer without a nil check and called through it from both closures:

```go
func Object[T, S any](name string, field func(*T) *S, schema *Schema[S]) Field[T] {
	return Field[T]{
		Decode: func(r *Reader, v *T) error {
			...
			return schema.Decode(r, field(v)) // schema may be nil
		},
		Encode: func(w *Writer, v *T) error {
			return schema.Encode(w, field(v)) // schema may be nil
		},
	}
}
```

A nil `*Schema` receiver reaches `s.rejectDuplicate` / `s.fields` / `s.decl`
inside `Schema.Decode`/`Schema.Encode` and panics with a nil-pointer
dereference. Every sibling constructor already turns the equivalent misuse into
an inspectable sentinel: `Slice`, `Map` and `Array` return
`errNilElementDecoder` / `errNilElementEncoder` for a codec missing a direction,
and `Schema.Encode` returns `errNoFieldEncoder` for a field with no encoder.
`Object` was the outlier, so a programming error crashed the program instead of
being reported.

## 2. Decision

Add the `errNilSchema` sentinel to `internal/codec/field.go` and check
`schema == nil` in both returned closures:

- **Encode** returns `errNilSchema` before any write. A nested struct field is
  always encoded as an object, so it always needs the schema.
- **Decode** returns `errNilSchema` after the `KindNull` branch. A JSON `null`
  leaves the field unchanged and needs no schema, which mirrors how a `null`
  container decodes without needing its element codec.

The sentinel is unexported, matching the other misuse sentinels in the package;
callers still observe it through the returned error, and the internal tests pin
it with `errors.Is`. Validation at construction time was rejected because
`Object` returns a `Field[T]` with no error channel, and a constructor panic is
exactly the behavior the task removes.

## 3. Alternatives considered

- **Panic in the constructor with a clear message.** Loud, but it restores the
  crash the task exists to eliminate, and the rest of the field constructors
  report misuse lazily from the closures.
- **Check before `Peek`.** Returns `errNilSchema` even for a JSON `null`, which
  would make the null path stricter than `Slice`/`Map`/`Array` and change the
  documented "a JSON null leaves the field unchanged" behavior.

## 4. Verification

- `TestObjectNilSchema` reproduces the panic first, then pins that decoding a
  non-null object and encoding through the field both return `errNilSchema`
  (reachable with `errors.Is`), and that a `null` member still decodes with no
  error and leaves the field unchanged.
- `make verify` (tests, `gofmt`, `go vet`, `golangci-lint`).
